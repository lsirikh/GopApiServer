| 항목 | 내용 |
|---|---|
| **무엇이 바뀌나** | "JWT 유효한가"만 보던 인증이 이제 **사용자 상태(active/locked) + 세션 상태**까지 검증 |
| **요청/응답 계약** | **무변경** — DTO·필드·URL 동일. 클라 **모델 수정 불필요** |
| **클라 영향** | 아래 상황에서 이전엔 통과하던 요청이 이제 **401** (정상 강화). 401 → 재로그인 흐름 확인 필요 |
| **정상 사용자** | 영향 없음 — 로그인·API·refresh 모두 그대로 동작 |

## 1. 이제 401을 반환하는 상황 (이전엔 통과)

| # | 상황 | 이전 | 이후 |
|---|---|---|---|
| 1 | 계정이 **잠김/비활성**된 후 기존 access token으로 API 호출 | 200(통과) | **401** |
| 2 | 계정이 잠김/비활성된 후 refresh 호출 | 200(새 토큰) | **401** |
| 3 | **세션이 종료/강제로그아웃**된 후 그 refresh token으로 refresh | 200(새 토큰) | **401** |
| 4 | **중복 로그인**(같은 계정 재로그인) 후, 이전 기기의 access **또는 refresh** | access만 401, refresh 통과 | **둘 다 401** |
| 5 | 관리자가 **비밀번호 초기화**한 후 대상 계정의 이전 access/refresh | 200(통과) | **둘 다 401** |
| 6 | refresh token에 **sid claim이 없는** 레거시 토큰으로 refresh | 200 | **401** (재로그인 필요) |

> 모두 HTTP **401** + 기존 에러 엔벨로프(`code: UNAUTHORIZED` 또는 `SESSION_REVOKED`). 형식 동일.

## 2. 클라 권장 조치

1. **401 → 재로그인 트리거**: access 호출이나 refresh에서 401을 받으면 **저장된 토큰을 폐기하고 로그인 화면으로**. (이미 대부분 구현돼 있을 것 — 이 변경으로 401 빈도가 "정상적으로" 늘 뿐, 새 코드 불필요.)
2. **refresh 실패 처리 확인**: refresh가 401이면 **더 이상 재시도하지 말고** 로그인으로. (이전엔 refresh가 거의 항상 성공했으나, 이제 세션 종료/잠금 시 401.)
3. **중복 로그인 UX**: 한 계정을 다른 기기에서 로그인하면 이전 기기가 **완전 로그아웃**(access+refresh 모두 무효). 다중 동시 세션이 필요하면 서버팀에 문의(현재는 "최신 로그인만 유효" 정책).
4. **요청/응답 DTO는 수정 불필요** — 회귀 확인만.

## 3. 정상 동작(무회귀) 보장

- 정상 active·unlocked 계정: 로그인 → API → refresh 전부 그대로 **200**.
- ADMIN 포함 모든 정상 사용자 영향 없음.
- 실측(Live E2E): 정상 refresh 200, 정상 로그인+API 200 확인.

## 4. 배경 (왜)

기존엔 계정을 잠그거나 세션을 강제 종료해도 **이미 발급된 토큰이 계속 유효**했습니다(토큰이 blacklist되지 않은 경우). 특히 refresh token은 세션 검증 없이 새 토큰을 발급해, 종료된 세션이나 이전 기기가 **부활**할 수 있었습니다. 이번 변경으로 **잠금·비활성·세션종료·비밀번호초기화·중복로그인**이 실제로 즉시 효력을 갖습니다.
